## LiteAPI v3.0 — hotel search

### Summary
LiteAPI v3.0 (base https://api.liteapi.travel/v3.0, header X-API-Key) can deliver far more than 6 hotels with no extra cost: GET /data/hotels defaults to 200 results (max 5000) and accepts server-side filters that map directly onto Rovyn's questionnaire (hotelTypeIds, starRating, minRating, minReviewsCount, facilityIds + strictFacilitiesFiltering, lat/long/radius >= 1000 m, aiSearch natural-language intent, placeId), and the list response already carries id, name, hotelDescription, address, city, country, lat/long, main_photo, thumbnail, stars, rating, reviewCount, hotelTypeId, chainId, chain, facilityIds and currency, so no per-hotel details call is needed to explain a pick. POST /hotels/rates accepts the same filters inline (can even skip /data/hotels and search by cityName+countryCode / lat-long-radius / aiSearch directly), has a default cap of 200 hotels (expandable to 5000 via limit), recommended timeout 6-12 s, maxRatesPerHotel to keep payloads small, includeHotelData to get a hotels[] summary block, sort top_picks|price|revenue, refundableRatesOnly, boardType, and a stream mode. POST /hotels/min-rates returns only the cheapest price + offerId per hotel and is positioned as the fast listing-page call. Static reference lists (/data/facilities, /data/hotelTypes, /data/chains) take no parameters. Sandbox keys are free, limited to 5 req/s (production 250 req/s, 429 on excess); search/content/prebook/book endpoints are free "subject to a reasonable look-to-book ratio" (an older FAQ cited 5000:1); only Places ($0.01/req) and Price Index ($0.05/req) endpoints are metered. Docs say sandbox "mirrors production" but do not state whether sandbox rates are live supplier inventory; sandbox bookings use the ACC_CREDIT_CARD simulated payment. Rovyn's current code (backend/services/hotel_service.py) uses only cityName+countryCode+limit=40 and an unfiltered /hotels/rates call with no timeout/maxRatesPerHotel, then truncates to 6 — the gap is entirely in parameters Rovyn does not send.

### Corrections applied after fact-checking
- All listed optional body fields and semantics are correct as stated, with two fixes: boardType accepts the comma-separated OR codes RO, BI, HB, FB, AI, DI, LI, BDI, BLI, LDI (add BLI); and the text "Default limit of 200 hotels (expandable to 5,000), recommended timeout of 6-12 seconds" appears in the endpoint's Key Features bullet list rather than as a page header. The second source (stream-hotel-rates guide) and the Node SDK README do not document the filter/sort fields at all, so the reference page remains the only primary source for them.

### Recommendations
WHAT ROVYN SHOULD DO
1. Keep the two-step flow but make it filter-aware. In real_stay_options build the GET /data/hotels query from the questionnaire: hotelTypeIds (join the ids from _VOTE_TYPE_IDS for every vote that got >=1 ballot, core+partial, so a mixed group gets a mixed pool), starRating derived from budget tier (e.g. budget -> "2.0,2.5,3.0,3.5", mid -> "3.0,3.5,4.0,4.5", luxury -> "4.5,5.0"), minReviewsCount=20 and minRating=7.0 (0–10 scale here) to cut junk, limit=150–300 (default is already 200 — Rovyn's limit=40 is the main reason the pool is thin). Prefer latitude/longitude/radius (>=1000 m, e.g. 3000–8000 m around the centre) over cityName when Rovyn already geocodes the destination — LiteAPI's own guide says this is "nearly always preferable" and cityName matching is fragile for multi-word or non-English cities. Pass countryCode in every call (required).
2. Run 2–3 small facet queries instead of one big one when votes are split, e.g. one call per voted accommodation type (hostel ids / hotel ids / rental ids), each limit=60, then union by id. This guarantees every vibe/type that got votes has candidates in the pool, which is the alignment problem the user is complaining about. Add vibe->facility mapping via facilityIds (fetch GET /data/facilities once, cache in a module-level dict with TTL ~24h, match names like "Bar", "Nightclub", "Spa", "Swimming pool", "Beachfront", "Fitness centre", "Restaurant", "Kitchen"); default non-strict (any-of) matching and only use strictFacilitiesFiltering=true for a single hard requirement.
3. Price every candidate with POST /hotels/min-rates first (hotelIds up to the whole pool, same occupancies, timeout 8–10). It is the documented fast path for listing pages and returns price + offerId per hotel; use its `price` to build the budget filter (there is NO minPrice/maxPrice param on rates) and rank. Then call POST /hotels/rates only for the 12–20 shortlisted hotels with maxRatesPerHotel=3, includeHotelData=true, timeout=10, refundableRatesOnly=false (but surface refundableTag in the UI), sort [{field:"top_picks"}] or [{field:"price",direction:"ascending"}]. If min-rates proves unreliable in sandbox, fall back to one /hotels/rates call with maxRatesPerHotel=1 on the full pool (200 hotels is the default cap, so chunk at 200).
4. Build the "why we picked it" explanation deterministically from fields already on the list response, no extra calls: hotelTypeId vs the group's votes (name the vote it satisfies), stars, rating/reviewCount ("8.6/10 from 1,204 reviews"), facilityIds mapped to names that intersect the group's vibes ("has a bar + rooftop pool for your nightlife vote"), distance from centre (haversine on latitude/longitude), price vs the per-person budget (offerRetailRate.amount / group_size vs budget), refundable (cancellationPolicies.refundableTag == "RFN") and board (boardName). Only call GET /data/hotel lazily when the user opens a card (rooms[], hotelImages[], poi[], sentiment_analysis.pros/cons are details-only and great for the "read more" drawer the user asked for).
5. Return 12–20 options with explicit diversity: at least 2 per voted accommodation type, spread across price terciles, and always include the cheapest and best-rated. Keep the current fallback-to-AI behaviour on any failure.
6. Transport: send timeout in the body (6–12 s recommended) and set urllib timeout slightly above it; treat HTTP 204 (error.code 2001 "no availability found") as an empty result, not an exception; handle 429 with backoff (sandbox is only 5 req/s — the per-type facet queries plus min-rates plus rates for a multi-city board can exceed it, so serialise calls with ~250 ms spacing in sandbox, or batch cities). Never put hotels in production calls you don't intend to book at a sane ratio — free tier is "reasonable look-to-book".

PITFALLS
- Parameter names differ between endpoints: list uses facilityIds + strictFacilitiesFiltering (comma-separated strings), rates uses facilities + strictFacilityFiltering (arrays). starRating is a string on the list and number[] on rates. minRating is 0–10 on /data/hotels but 0–5 on /hotels/rates.
- offerRetailRate.amount is the whole offer (all occupancies, whole stay) — keep the current per-person math. offerId is the booking handle for prebook; it is long and session-bound, do not persist it across days.
- suggestedSellingPrice may differ from offerRetailRate (margin/markup); decide which one is the customer price before the Stripe/MoR work.
- Sandbox: docs say it mirrors production but do not promise live supplier rates; responses carry sandbox:true — log it, and expect hotels that 200 with empty roomTypes. Production key requires a card on file and switches the dashboard toggle.
- Places (placeId) and Price Index endpoints are the only metered hotel calls ($0.01 / $0.05 per request) — avoid /data/places; geocode elsewhere.
- Do not rely on aiSearch alone for alignment: it is a semantic ranking input with undocumented behaviour; use it as an optional extra signal (e.g. aiSearch="lively nightlife area near the beach") and keep the deterministic filters authoritative.
- hotelTypeId values in Rovyn's _TYPE_NAMES are a local snapshot; re-pull GET /data/hotelTypes at startup and log drift.
- Keep hotelIds per /hotels/rates call <= 200 (default limit) and shard beyond that; the docs do not state a hard max for min-rates, so shard at 200 there too.

## LiteAPI v3.0 — booking (merchant of record)

### Summary
LITE-BOOK findings (LiteAPI v3.0, now branded "Nuitee Connect"; base URL https://book.liteapi.travel/v3.0, header X-API-Key). Booking is two calls: POST /rates/prebook (offerId + usePaymentSdk) then POST /rates/book (prebookId + holder + guests + payment). Three payment modes matter for Rovyn: (1) Nuitee-as-merchant via Payment SDK / Stripe Elements: prebook with usePaymentSdk=true returns secretKey (a Stripe PaymentIntent client secret on LiteAPI's Stripe platform) + transactionId, traveler pays, book with payment.method="TRANSACTION_ID"; LiteAPI captures funds and pays Rovyn its `margin` commission weekly after checkout. (2) Rovyn-as-merchant-of-record: search rates with margin:0 (net rates), collect the traveler's money on Rovyn's own Stripe (authorize with manual capture), book with payment.method="ACC_CREDIT_CARD" (charges the credit card attached to Rovyn's LiteAPI production account, "available to everyone"), then capture the Stripe PaymentIntent only after the book call returns CONFIRMED and release it on failure — this is exactly the "Prebook → Payment Intent → Book → Confirm Intent" sequence LiteAPI's own integration guide recommends. "CREDIT" (credit line, invoiced periodically) is the enterprise variant and needs a signed contract/credit check and does not work in sandbox. (3) WALLET: the enum still exists on /rates/book ("uses available wallet balance"), but the live FAQ states verbatim "Wallet bookings are no longer supported" while adjacent FAQ lines still say "fund the wallet and go live"; there is NO documentation anywhere on funding a wallet, and no sandbox wallet simulation — treat WALLET as unavailable and use ACC_CREDIT_CARD instead. A prebook `payment.useOwnSecretKey: true` flag exists ("create the PaymentIntent on the partner's Stripe account (requires configured Stripe keys)") but is undocumented beyond the schema; it would let the Stripe-SDK flow run on Rovyn's Stripe account — confirm with LiteAPI support before relying on it. Prebook hold duration is NOT documented (only "a short period"); the Stripe card hold auto-releases 1 hour after prebook if book is never called. hotelConfirmationCode is NOT returned at book time (Nuitee obtains it manually; subscribe to webhook booking.book.hotelConfirmationNumber or poll GET /bookings/{id}). Cancel is PUT /bookings/{bookingId} with no body; response has status CANCELLED or CANCELLED_WITH_CHARGES plus cancellation_fee and refund_amount. Sandbox: key prefix sand_, production prod_; every sandbox key carries a hidden test ACC_CREDIT_CARD so sandbox bookings are free; SDK test card 4242 4242 4242 4242; sandbox 5 req/s, production 250 req/s. Production needs a credit card attached in the dashboard (unlocks prod key) and a payout method; core Rates→Prebook→Book endpoints are free. Webhooks are dashboard-registered, envelope {event_id, event_name, request(string JSON), response(string JSON), sandbox}; optional shared token in `authorization` header; exponential-backoff retries; cancel/refund webhooks fire only in production. "Vouchers" in LiteAPI are discount codes, not booking confirmation documents; no voucher-PDF endpoint exists — Rovyn must render its own confirmation from GET /bookings/{id}.

### Corrections applied after fact-checking
- Prebook 200 response: top-level fields are `data` and `guestLevel` (integer, "Used with loyalty programs to determine the guests level of cost reduction") only — there is NO top-level `sandbox` field on the prebook response; `sandbox` (boolean) is a top-level field of the POST /rates/book response instead. All listed data.* fields, required set, types and quoted descriptions are otherwise correct as stated.

  envelope: { event_id, event_name, request:"<stringified JSON>", response:"<stringified JSON>", sandbox:true|false } → JSON.parse(body) then JSON.parse(request/response).
  hotel events: booking.prebook, booking.book, booking.cancel, booking.book.hotelConfirmationNumber, booking.checkinInstruction, booking.prebook_error, booking.book_error, booking.cancel_error, booking.rebook.rfn, booking.rebook.nrfn, booking.amendment, booking.amendment.relocation, booking.refund, booking.compensation. ### Recommendations
1. Do NOT build on WALLET. The /rates/book enum still lists it, but the live FAQ says "Wallet bookings are no longer supported" and no page documents funding, bank transfer, minimums or a sandbox balance. The documented merchant-of-record path is payment.method="ACC_CREDIT_CARD" (LiteAPI charges a credit card attached to Rovyn's production account at booking time) and, at scale, "CREDIT" (invoiced credit line after a contract/credit check). Ask LiteAPI support in writing whether the wallet is really retired and whether a prepaid balance can replace the card (relevant to card-spend limits and 1-3% card fees on net rates).

2. Prototype in sandbox with ACC_CREDIT_CARD: every sand_ key has a hidden test card, so a full search → prebook → book → GET → PUT cancel loop costs nothing and needs no Stripe keys from LiteAPI. Keep Rovyn's own Stripe in test mode in parallel (manual-capture PaymentIntent). This gives an end-to-end demo without any LiteAPI enablement.

3. Implement the exact "Prebook → Payment Intent → Book → Confirm Intent" sequence from LiteAPI's integration guide: authorize on Rovyn's Stripe with capture_method=manual, call book, capture only on status=CONFIRMED, cancel the intent on any failure. A Stripe authorization lasts ~7 days, far longer than LiteAPI's undocumented prebook window, so re-run prebook immediately before book and check priceDifferencePercent==0, cancellationChanged==false, boardChanged==false.

4. Idempotency and the "unknown" state: generate and persist a unique clientReference before book; let book run the full ~2 minutes (stdlib urllib timeout ≥120 s); on a client timeout never assume failure — re-POST with the same clientReference (4005 means it exists) and/or list bookings by customTags TRIP_ID, then capture or release the Stripe hold. Tag every booking with customTags (≤5, upper-case keys) so GET /bookings/ can be filtered per trip.

5. Pricing when Rovyn is MoR: request rates with margin:0 so retailRate.total is the net amount LiteAPI will charge Rovyn; add Rovyn's fee in Stripe. Never show a room publicly below suggestedSellingPrice (CUG rule) — inside a logged-in trip group is a closed user group, but marketing pages are not. Rovyn earns the spread immediately; no LiteAPI payout is involved. If Rovyn instead uses the Payment SDK/Stripe Elements path (Nuitee as MoR), commission is paid weekly only after guest checkout and Rovyn gets no Stripe webhooks.

6. Explore prebook payment.useOwnSecretKey:true + gateway:"STRIPE": the schema says it creates the PaymentIntent on the partner's (Rovyn's) Stripe account, which would make Rovyn MoR while LiteAPI handles capture; the setup ("configured Stripe keys") is undocumented — ask the account manager. Until confirmed, treat ACC_CREDIT_CARD as the only self-serve MoR route.

7. hotelConfirmationCode is never present at book time (Nuitee obtains it manually). Store bookingId as the canonical reference, show "confirmation pending from hotel", and register a dashboard webhook for booking.book, booking.book.hotelConfirmationNumber, booking.checkinInstruction, booking.cancel, booking.refund, booking.book_error. Parse the envelope (request/response are stringified JSON), verify the shared token in the `authorization` header, dedupe on event_id, and keep a daily GET /bookings/{id} poll as fallback (cancel/refund webhooks do not fire in sandbox).

8. Cancellation/refunds as MoR: PUT /bookings/{id} returns refund_amount and cancellation_fee; LiteAPI refunds Rovyn's card, Rovyn must refund the traveler on Stripe. Compute the traveler-facing policy from cancelPolicyInfos (amount = charge after cancelTime; latest-passed policy wins; drop 0-amount nodes; NRFN may still be partly refundable) and surface lastFreeCancellationDate in the UI before purchase. Rovyn's own fee refund policy must be stated in its terms.

9. Compliance: LiteAPI is SAQ A and never sees card data in these flows; Rovyn stays SAQ A too as long as cards are entered only through Stripe Elements/Checkout and Rovyn never calls the pci-book CREDIT_CARD endpoint. Being MoR makes Rovyn the seller for chargebacks, consumer refunds, tax/VAT on its fee, and (in the EU/UK) Package Travel rules if flights + hotel are sold together — out of LiteAPI's scope; handle in the legal runbook.

10. Operational limits: sandbox 5 rps, production 250 rps (429 → exponential backoff); core booking endpoints free, places $0.01/req, price index $0.05/req; keep a sane look-to-book ratio or usage can be surcharged. Go-live checklist: attach a credit card (unlocks prod_ key), set a payout method, confirm the dashboard sandbox/prod toggle, register production webhooks, and do one real refundable booking + cancel to validate the money loop.

Documentation pitfalls spotted: FAQ contradicts itself on wallets; status spelling varies (CANCELED in schemas vs CANCELLED in examples / cancel response); GET /bookings/ uses snake_case while single-booking uses camelCase; the 204 not-found returns a JSON body; no numeric prebook validity is published anywhere.

## Duffel Flights API v2

### Summary
Duffel Flights API (Duffel-Version v2, base https://api.duffel.com, bodies and responses wrapped in a top-level `data` key) is a fit for Rovyn's "collect money on our own Stripe, pay Duffel from a prepaid balance" model. Test mode is self-serve, costs nothing, and has an unlimited balance; live mode needs email verification + KYC in the dashboard, a prepaid balance topped up by bank transfer, and a card on file for month-end platform fees. Pricing (pricing page, USD): $3.00 per confirmed order + 1% of order value (Managed Content) + $2.00 per paid ancillary + 2% FX when conversion is needed + $0.005 per excess search above a 1500:1 search-to-book ratio. Flow: POST /air/offer_requests (slices/passengers/cabin_class/max_connections) -> GET /air/offers/{id} to refresh the offer (offers expire, typically within 30 min; `expires_at`) -> charge the customer yourself -> POST /air/orders with `selected_offers` (exactly one), full passenger details keyed by the offer-request passenger `id`, and `payments: [{type:"balance", amount, currency}]` for an instant order, or `type:"hold"` with no `payments` when `payment_requirements.requires_instant_payment` is false, then POST /air/payments before `payment_required_by`. Price-change and expiry errors are 422s with codes `price_changed`, `offer_no_longer_available`, `offer_expired`, `payment_amount_does_not_match_order_amount`, `order_creation_already_attempted`. Cancellation is two-step (create pending cancellation -> confirm) with `refund_amount`/`refund_to` ("balance" when paid from balance) so Rovyn must refund the traveller on Stripe itself. Rate limit is 60 requests per 60-second window with ratelimit-* headers. Test scenarios are triggered by specific origin/destination pairs (e.g. JFK->EWR holdable, LHR->STN price change, LGW->STN insufficient balance). Important discrepancy found: the official JS SDK's TypeScript type lists `type: 'instant' | 'pay_later'` while the current docs/guides use `'hold'`; use `'hold'` per the docs and verify in test mode. US DOT 14 CFR 399.84 requires the displayed price to be the entire price including Rovyn's fee and taxes, and bans pre-ticked optional extras.

### Corrections applied after fact-checking
- Live-mode activation: verify email first, then a verification section (business type, personal details, business information, KYC). Card details for automatic payment of the monthly invoice go in Settings > Billing; without the Payments API you can top up the Balance and use just the Flights API. The Balance page shows available funds, lets you top up (via "Top-up balance" -> bank transfer with a unique reference), view/export transactions, and set a low-balance email threshold (Settings > Balance; defaults £1000 / €1100 / $1300 / A$1500). Payouts/withdrawals are NOT self-service: per Duffel's help centre you must email help@duffel.com to initiate a withdrawal, and funds are returned to the original top-up payment method.
- The Duffel Balance is a prepaid account funded only by bank transfer (Balance page → 'Top-up balance' shows bank details and a unique reference; funds credited within one working day of arrival). There is no first-vs-subsequent top-up distinction and Duffel Payments does not top up the Balance — it is a separate route where customer card payments flow to Duffel to pay the airline (you can switch between the two per order). An order cannot be created until the Balance covers it. The card on file (Settings > Usage and billing) is used solely to charge platform fees at month end; Duffel Payments fees are charged separately when a payment intent is confirmed.

### Recommendations
1. Money flow for Rovyn as merchant: customer pays Rovyn on Stripe (Rovyn is MoR on the card statement, owns chargeback/fraud/airline-insolvency liability per Duffel's MoR article); Rovyn pays Duffel from a prepaid balance (`payments[].type = "balance"`). Keep a balance float sized to a few days of bookings and set the dashboard low-balance alert; `insufficient_balance` (422) is a hard failure at order/payment time. Refunds come back to the balance, never to the customer, so Rovyn must issue the Stripe refund itself and reconcile.
2. Prefer the hold-then-pay pattern when `payment_requirements.requires_instant_payment` is false: create the hold order first (no money moves), run the Stripe PaymentIntent (manual capture), then POST /air/payments. If Stripe fails, let the hold lapse at `payment_required_by`. For instant-only offers, capture Stripe first (per Duffel: 'charge the customer yourself before creating the order') and handle a post-capture Duffel 422 by refunding Stripe automatically.
3. Always re-GET /air/offers/{id} immediately before showing the checkout price and again before creating the order; compare `total_amount` to what was quoted and re-confirm with the user if it changed. Handle `offer_expired`/`offer_no_longer_available`/`price_changed`/`order_creation_already_attempted` by re-searching, never by retrying the same offer.
4. Idempotency: Duffel has no idempotency-key header on this track. Guard with your own DB lock per `offer_id` and never retry POST /air/orders or /air/payments on timeout/5xx; instead GET /air/orders?… / check dashboard and contact support with `meta.request_id`. Set urllib timeout >= 130 s for those two calls and run them in a background task, not the request thread.
5. Passenger data to collect at checkout: given_name, family_name, born_on, gender (m/f), title (mr/ms/mrs/miss), per-passenger email and E.164 phone; add identity documents if `passenger_identity_documents_required`. Passenger `id`s come from the offer request, so persist the offer-request passenger ids with each trip member. Infants need `infant_passenger_id` to a unique adult.
6. Breadth of results: to widen flight options, run one offer request per cabin class / with `max_connections` 0,1,2 and merge, use `view=itineraries` for grouping, paginate `GET /air/offers?offer_request_id=`, and raise `supplier_timeout` toward 60000 ms. Watch the 1500:1 search-to-book ratio (excess-search fee $0.005) and the 60 req/min limit: back off on 429 using `ratelimit-reset`.
7. Pricing display and DOT compliance (14 CFR 399.84): show one all-in price = offer.total_amount + Rovyn's service fee + Stripe-passed costs; taxes may be itemised but not prominently; never pre-tick optional bags/seats/insurance (opt-in only); do not label each-way-of-round-trip fares as 'one-way'. Display `operating_carrier.name` for every segment on the first offer screen and in confirmations; link `owner.conditions_of_carriage_url`; display Duffel's required legal notices (help article 360021056640, not fetched here). Rovyn, not the airline, must send the booking confirmation (itinerary, payment, booking_reference).
8. Explain-why data for the UI is all on the offer: `owner.name`, `slices[].duration`, segment count (connections), `departing_at`/`arriving_at`, `conditions` (refundable/changeable + penalty), `fare_brand_name`, `total_emissions_kg`, baggage via `segments[].passengers[].baggages`. Treat a null condition as 'unknown', not 'not allowed'.
9. Go-live checklist: (a) dashboard email verification + KYC (business type, personal and business details); (b) create a read-write live token, keep it server-side only; (c) add billing card in Settings->Billing; (d) first balance top-up by bank transfer; (e) budget $3/order + 1% of fare + 2% FX (price in the billing currency to avoid FX) + $2 per paid ancillary; (f) set low-balance threshold; (g) register webhooks `order.created`/`order.creation_failed` if card payments are ever used.
10. Pitfalls: the JS SDK types (`'pay_later'`) disagree with the docs (`'hold'`) for order `type`; verify with the JFK->EWR test route before shipping. `payment.currency` for balance orders is your organisation's billing currency, so pick the Duffel billing currency to match Stripe's settlement currency. `documents[]` may be empty until ticketing completes; poll GET /air/orders/{id}. Help-center pages block automated fetches (403), so the balance/MoR/go-live claims above are from search snippets of those articles (medium confidence) and should be re-read in a browser.

### Recommendations
1) Integration shape for Rovyn (FastAPI + urllib): add `backend/providers/duffel_stays.py` with a thin client: `_request(method, path, body)` that sets the five headers, gzip-decodes, parses the {"data":...}/{"errors":...} envelope, surfaces meta.request_id, and on 429 sleeps until `ratelimit-reset` (parse as HTTP-date) then retries once; never retry POST /stays/bookings. Normalize each Duffel search result into Rovyn's existing hotel DTO: provider="duffel", provider_id=accommodation.id, offer_id=result.id (srr_), name, lat/lon from accommodation.location.geographic_coordinates, address from location.address, star_rating=rating, review_score (/10), review_count, photos=[p.url], amenities=[a.type], description, price_total=cheapest_rate_total_amount + cheapest_rate_currency, expires_at. Keep LiteAPI as source #1 and dedupe across providers by (normalized name + ~100 m coordinate distance) so the same property doesn't show twice; prefer the cheaper total and keep both provider ids so booking can route to either.

2) Widening the range: Duffel search has no pagination and no documented result cap, so one call per destination with radius 5–10 km is enough; run it in parallel with LiteAPI (threads) and merge. Use the questionnaire votes to drive the Duffel filters that exist (`free_cancellation_only`, `instant_payment=true` when the group wants to pay in-app, guests[] with real adult/child counts, `rooms`), and derive the "why this was picked" explanation from fields that are actually present: amenities[].type (pool, spa, gym, pets_allowed, wifi, restaurant), review_score/review_count, rating, brand/chain, board_type/benefits (breakfast_included) from fetch_all_rates, cancellation_timeline (free cancellation until X), distance to the group's chosen anchor point. Do NOT trust rooms/rates in the search response for anything but a teaser; call fetch_all_rates only for the shortlisted cards (it is per result and counts against the rate limit).

3) Rate limits: assume ~10 search req/60 s in live mode (help-centre figure, unverified) and 60/60 s elsewhere; cache search results keyed by (lat, lon, radius, dates, guests) until `results[].expires_at`, and cache fetch_all_rates per srr_ id until rate.expires_at. Expose the limit headers in logs.

4) Booking/payment flow for the Merchant-of-Record prototype: (a) POST /stays/quotes {rate_id} immediately before taking payment; compare quote.total_amount/total_currency with what the user saw and re-confirm if changed; (b) charge the group via Stripe for quote.total_amount (+ Rovyn margin) and only on Stripe success call POST /stays/bookings with `payment` OMITTED (pay from Duffel balance) — this is the MoR path: Rovyn holds the customer funds, Duffel debits Rovyn's pre-funded balance. Keep `metadata` = {rovyn_trip_id, rovyn_booking_id} (≤40/≤500 chars) and store booking.id, booking.reference (hotel confirmation), status, confirmed_at, deposit_amount, due_at_accommodation_amount, key_collection.instructions, and the winning rate's cancellation_timeline. (c) Show the user: hotel ref, what is due at the property (due_at_accommodation_amount) and any deposit, check-in times, key collection instructions, cancellation deadlines — Duffel requires the confirmation page to display the content of its example page. (d) Cancellation: compute the refundable amount client-side from cancellation_timeline (entry with before > now), call POST /stays/bookings/{id}/actions/cancel, then refund that amount via Stripe; there is no refund figure in the cancel response, so persist the timeline at booking time.

5) Pitfalls: `payment_type` can be guarantee/deposit (card guarantees, pay at hotel) — if Rovyn wants everything paid in-app, search with instant_payment=true and reject rates whose available_payment_methods lacks "balance". Stays guests have no born_on/age at booking (ages only go in the search guests[]). `email`/`phone_number` on accommodation are null until booked. fraud_error 422 is final; a 5xx on booking must be reconciled with GET /stays/bookings (list, filter by metadata) rather than retried. The quote has no documented expiry — rely on rate.expires_at and re-quote if more than a few minutes pass. Amounts are strings; use Decimal. 2% FX fee if the rate currency differs from the balance currency — keep the Duffel balance in the currency you sell in (likely USD) or price the fee in.

6) Enablement/legal runbook steps: (1) create Duffel account, generate a duffel_test_ token, prove the whole flow against lat -24.38/lon -128.32 test hotels (balance success, rate-unavailable, payment-declined rooms); (2) request Stays access via duffel.com/contact (separate from Flights); ask Sales for the profit-share %, settlement timing (paid after checkout), and the live search rate limit; (3) before go-live: add a card to the account, top up the Duffel balance by bank transfer sized to expected daily hotel volume (bookings fail if balance is short), confirm whether Rovyn needs card-payment approval at all (not needed for the balance/MoR model); (4) set the team support email (Duffel notifies it when key-collection details must be forwarded); (5) record x-request-id for every booking call for support escalations.
